# Техническое описание решения

## 1. Архитектура и разделение пакетов

Проект разделён на небольшие пакеты с одной основной ответственностью.

Основной поток данных имеет следующий вид:

```text
policy YAML/JSON
    ↓
internal/policy
    ↓
internal/alphabet
    ↓
internal/app.Prepare
    ↓
internal/generate
    ↓
internal/rules
    ↓
internal/strength
    ↓
internal/issue
    ↓
internal/history
    ↓
internal/report
```

### `cmd/pwp`

Содержит CLI-команды и маршрутизацию аргументов.

CLI не реализует алгоритмы генерации, проверки или истории самостоятельно. Команды адаптируют параметры командной строки к уже существующим внутренним API.

Для разбора параметров используется стандартный `flag.FlagSet` с `flag.ContinueOnError`.

Основные коды возврата:

```text
0 — успех
1 — содержательное несоответствие
2 — ошибка входных данных или выполнения
```

### `internal/policy`

Отвечает за:

* чтение YAML и JSON;
* строгую проверку неизвестных полей;
* применение значений по умолчанию;
* валидацию схемы;
* разбор duration;
* проверку разрешимости политики.

Неразрешимая политика должна быть отклонена до начала генерации.

### `internal/alphabet`

Строит фактические алфавиты классов:

* работает с Unicode-рунами;
* применяет `exclude`;
* обнаруживает повторяющиеся символы;
* обнаруживает пересечение классов;
* строит объединённый алфавит.

Результат построения затем переиспользуется генератором, проверкой правил и оценкой стойкости.

### `internal/random`

Содержит интерфейс источника случайности и unbiased-примитивы.

```go
type Source interface {
	Read(p []byte) (int, error)
}
```

Production source:

```go
crypto/rand.Reader
```

Пакет предоставляет выбор случайного значения из диапазона и Fisher-Yates shuffle без modulo bias.

### `internal/generate`

Отвечает только за построение кандидатов паролей.

Одна попытка включает:

1. выбор длины;
2. выполнение минимумов классов;
3. заполнение оставшихся позиций;
4. перемешивание;
5. проверку запретов.

Генератор ограничен `attempts` и не ослабляет политику при неудаче.

### `internal/rules`

Содержит проверку:

* длины;
* минимумов классов;
* `repeat_run`;
* `repeat_total`;
* алфавитных последовательностей;
* клавиатурных последовательностей по встроенным и пользовательским таблицам раскладок;
* словаря;
* контекста.

Диагностика содержит правило, offset и length, но не саму секретную подстроку.

### Клавиатурные таблицы

Для проверки `sequences.keyboard` поддерживаются встроенные таблицы:

```text
qwerty
jcuken
```

Кроме встроенных раскладок значение из `forbid.sequences.layouts` может быть путём к пользовательскому файлу таблицы.

Пользовательские таблицы загружаются один раз на этапе `internal/app.Prepare`, а не при каждой проверке пароля. После загрузки они передаются в `rules.Options` как уже подготовленные строки рун. Поэтому файловый ввод-вывод не выполняется внутри `rules.Check` и не добавляется к стоимости каждой проверки кандидата.

Формат пользовательского файла намеренно простой: одна непустая строка UTF-8 соответствует одному ряду клавиатуры.

Например:

```text
1234567890
qwertyuiop
asdfghjkl
zxcvbnm
```

Внутреннее представление таблицы:

```text
[][]rune
```

что соответствует модели проверки последовательностей по отдельным рядам.

Пустые строки пропускаются. Последовательность может идти по одному ряду в прямом или обратном направлении, но переход с одного ряда на другой последовательностью не считается.

Перед преобразованием строки в руны проверяется корректность UTF-8. Нечитаемый файл, некорректный UTF-8 или файл без непустых строк приводит к ошибке подготовки политики.

Имена `qwerty` и `jcuken` распознаются как встроенные таблицы и не читаются с диска. Остальные значения `layouts` интерпретируются как пути к пользовательским файлам.

Такое разделение сохраняет прежний алгоритм проверки клавиатурных последовательностей: встроенные и пользовательские layouts различаются только способом получения таблицы, а сама проверка работает с одинаковым представлением рядов.


### `internal/dictionary`

Отвечает за загрузку словаря, нормализацию и поиск словарных подстрок.

После загрузки словарь представлен trie и не перебирается линейно при каждой проверке пароля.

### `internal/strength`

Отвечает за оценку количества возможных исходов генерации, измерение rejection rate и вычисление нижней оценки энтропии политики.

Здесь же проверяется достаточность энтропии для `history.window`.

### `internal/issue`

Содержит:

* выдачу нового пароля;
* проверку history window;
* пул предгенерированных паролей;
* hot reload конфигурации пула.

### `internal/history`

Содержит persistent history store:

* `Record`;
* соль и hash;
* `Save`;
* `List`;
* `Reuse`;
* атомарный `Accept`;
* metadata;
* garbage collection;
* rotation plan;
* `verify`.

Для хранения используется bbolt.

### `internal/report`

Создаёт детерминированные JSON- и HTML-отчёты.

HTML формируется через `html/template`.

### `internal/atomicfile`

Используется там, где выходной файл не должен оставаться частично записанным после ошибки.

### `internal/secret`

Содержит функцию затирания контролируемых `[]byte`, содержащих секретные значения.

# 2. Выборка случайного значения без смещения

Прямое вычисление:

```text
randomValue % n
```

не используется, поскольку оно создаёт modulo bias, если размер пространства источника не делится на `n` без остатка.

Реализация использует rejection sampling.

Для диапазона:

```text
[0, n)
```

сначала определяется минимальное количество байтов `k`, достаточное для представления `n - 1`.

Размер пространства случайного значения:

```text
space = 2^(8k)
```

После этого вычисляется:

```text
bucketSize = floor(space / n)
usableLimit = bucketSize * n
maxAccepted = usableLimit - 1
```

Случайное значение читается из источника.

Если:

```text
randomValue > maxAccepted
```

значение относится к неполному хвосту пространства и отбрасывается.

Для принятого значения индекс вычисляется как:

```text
index = randomValue / bucketSize
```

Таким образом, каждому значению из `[0, n)` соответствует ровно `bucketSize` исходных случайных значений.

Вероятности всех результатов одинаковы.

Например, для `n = 10` и одного случайного байта:

```text
space = 256
bucketSize = floor(256 / 10) = 25
usableLimit = 250
```

Принимаются значения:

```text
0..249
```

а:

```text
250..255
```

отбрасываются.

Каждому из десяти выходных индексов соответствует ровно 25 входных значений.

При использовании восьми байтов расчёт выполняется отдельно с помощью операций `math/bits`, чтобы не получить overflow при представлении пространства `2^64`.

Этот же механизм используется:

* при выборе длины пароля;
* при выборе символов;
* при выборе индексов Fisher-Yates shuffle.

Дополнительно существует детерминированный тест с подставным источником, который специально сначала отдаёт значение из rejected tail, а затем допустимое значение. Тест проверяет, что первое значение действительно отбрасывается и выполняется повторное чтение.

# 3. Статистическая проверка равномерности

Корректность unbiased random primitives проверяется не только детерминированными unit-тестами rejection sampling, но и отдельными статистическими тестами на равномерность.

Для проверки используется критерий согласия Pearson χ².

Статистика рассчитывается по формуле:

```text
χ² = Σ((observed_i - expected_i)² / expected_i)
```

где:

```text
observed_i
```

— фактическое количество наблюдений в категории, а:

```text
expected_i
```

— ожидаемое количество наблюдений при равномерном распределении.

Для равновероятных категорий:

```text
expected = sampleCount / categoryCount
```

Нулевая гипотеза состоит в том, что наблюдаемое распределение соответствует равномерному.

## Уровень значимости

Для статистических тестов используется:

```text
alpha = 1e-10
```

Такой уровень выбран намеренно намного строже обычных статистических значений вроде `0.05`.

При `alpha = 0.05` корректная реализация случайного генератора могла бы случайно проваливать тест примерно в 5% независимых запусков, что неприемлемо для автоматического CI.

При:

```text
alpha = 1e-10
```

вероятность ложного отклонения корректной реализации для одной χ²-проверки составляет порядка:

```text
10^-10
```

Даже с несколькими независимыми проверками суммарная вероятность случайного падения остаётся пренебрежимо малой.

Для проверки используются следующие critical values верхнего хвоста χ²-распределения:

```text
df = 4  -> 52.68
df = 7  -> 60.90
df = 9  -> 65.82
```

Фактическая χ²-статистика должна быть меньше соответствующего critical value.

Все тесты используют выборки, для которых ожидаемое количество наблюдений в каждой категории значительно превышает минимально рекомендуемое значение 5.

## Распределение символов по позициям

Тест:

```text
internal/generate/statistics_test.go
TestGeneratedCharacterDistributionChiSquare
```

генерирует:

```text
250 000 паролей
```

фиксированной длины:

```text
4
```

из алфавита:

```text
0123456789
```

Таким образом, для каждой позиции существует:

```text
10
```

возможных символов.

Для каждой позиции отдельно подсчитывается, сколько раз встретился каждый символ.

Ожидаемое количество наблюдений одного символа в одной позиции:

```text
250000 / 10 = 25000
```

Для каждой из четырёх позиций вычисляется отдельная χ²-статистика с:

```text
df = 10 - 1 = 9
```

и порогом:

```text
65.82
```

Тест проверяет именно распределение символов **по каждой позиции отдельно**, поэтому корректное суммарное распределение не может скрыть систематическое смещение отдельных позиций.

## Равномерность выбора длины

Тест:

```text
internal/generate/statistics_test.go
TestChooseLengthDistributionChiSquare
```

выполняет:

```text
1 200 000
```

выборов длины из диапазона:

```text
12..16
```

То есть возможны пять значений:

```text
12
13
14
15
16
```

При корректном равномерном выборе ожидаемая частота каждой длины:

```text
1200000 / 5 = 240000
```

Количество степеней свободы:

```text
df = 5 - 1 = 4
```

Используемый critical value:

```text
52.68
```

Тест подтверждает, что выбор длины через общий unbiased random primitive не имеет статистически обнаружимого смещения.

## Равномерность Fisher-Yates shuffle

Тест:

```text
internal/random/statistics_test.go
TestShufflePositionDistributionChiSquare
```

проверяет распределение позиций после перемешивания.

Используется набор из восьми уникальных элементов:

```text
0 1 2 3 4 5 6 7
```

Выполняется:

```text
250 000
```

независимых перемешиваний.

Для каждого исходного элемента подсчитывается, сколько раз он оказался в каждой из восьми конечных позиций.

При равномерном Fisher-Yates shuffle ожидаемая частота попадания конкретного элемента в конкретную позицию:

```text
250000 / 8 = 31250
```

Для каждого из восьми исходных элементов выполняется отдельная χ²-проверка:

```text
df = 8 - 1 = 7
```

с critical value:

```text
60.90
```

Такая проверка сильнее простой проверки количества случаев, когда элемент остался на исходной позиции: тестируется всё распределение его конечной позиции.

## Источник случайных данных в статистических тестах

Статистические тесты используют байты из:

```go
crypto/rand
```

Перед основной проверкой случайные данные читаются в крупный буфер, после чего тестируемые функции получают их через:

```go
bytes.Reader
```

Это позволяет сохранить равномерный криптографический источник и одновременно избежать сотен тысяч отдельных системных вызовов `crypto/rand` во время статистического теста.

## Дополнительные детерминированные проверки

Статистические тесты не заменяют детерминированные unit-тесты.

Отдельно проверяются:

* отбрасывание значения из неполного хвоста rejection sampling;
* повторное чтение после rejected value;
* распространение ошибки источника случайности;
* корректность границ диапазона;
* работа Fisher-Yates shuffle;
* отсутствие использования `math/rand` в исходниках проекта.

Таким образом, проверка unbiased random implementation состоит из двух уровней:

1. детерминированные тесты проверяют конкретную механику алгоритма;
2. χ²-тесты проверяют фактическое статистическое распределение большого числа результатов.

Такой подход позволяет одновременно обнаруживать логические ошибки реализации и систематическое статистическое смещение.

# 4. Структура словаря и сложность поиска

Для словаря используется trie — префиксное дерево.

Узел имеет вид:

```go
type trieNode struct {
	children map[rune]*trieNode
	terminal bool
}
```

`terminal` отмечает окончание словарного слова.

При загрузке каждое слово добавляется в дерево по одной руне.

Если суммарная длина всех слов словаря в рунах равна `D`, построение trie имеет ожидаемую сложность:

```text
O(D)
```

при ожидаемой константной стоимости доступа к `map`.

Память также пропорциональна количеству созданных trie-узлов:

```text
O(D)
```

с учётом общего использования префиксов.

## Поиск

Проверка начинается с каждой позиции пароля.

От текущей позиции выполняется переход по trie до первого отсутствующего ребра.

Если текущий узел имеет:

```text
terminal = true
```

фиксируется словарное совпадение.

Если длина пароля равна `L`, а максимальная глубина реально проверяемого префикса равна `W`, сложность поиска:

```text
O(L * W)
```

В худшем случае `W <= L`, поэтому верхняя граница для одного пароля:

```text
O(L²)
```

Ключевое свойство состоит в том, что после построения trie поиск не является:

```text
O(number_of_dictionary_words)
```

для каждой позиции пароля.

Размер словаря влияет в основном на размер построенного дерева, а не на необходимость последовательного перебора всех слов.

Это подтверждается benchmark:

```text
1 000 слов:
419.3 ns/op
112 B/op
2 allocs/op

1 000 000 слов:
465.6 ns/op
112 B/op
2 allocs/op
```

При увеличении словаря в 1000 раз время поиска увеличилось примерно на 11%, а объём аллокаций одной операции не изменился.

Это подтверждает отсутствие линейной зависимости времени поиска от количества слов словаря.

# 5. Метод оценки стойкости политики

Оценивается стойкость процесса генерации политики, а не отдельного уже известного пароля.

Результат представлен структурой:

```go
type Estimate struct {
	Bits          float64
	Outcomes      *big.Int
	Samples       int
	Rejected      int
	RejectionRate float64
}
```

Оценка состоит из двух частей.

## 5.1. Число исходов до запретов

Для каждого класса учитываются:

* размер алфавита;
* минимальное количество символов;
* возможное количество символов этого класса;
* размещение символов между позициями;
* `repeat_total`.

Расчёт выполняется через dynamic programming и `math/big.Int`, поэтому число комбинаций не ограничено размером обычного integer.

При разрешённых повторах количество способов выбрать `k` символов из класса размера `m`:

```text
m^k
```

При:

```text
repeat_total = true
```

используется число размещений без повторений:

```text
P(m, k) = m! / (m - k)!
```

Для объединения классов учитывается число способов расположить очередную группу символов среди уже выбранных позиций через биномиальный коэффициент.

Количество допустимых исходов суммируется для всех длин:

```text
length.min .. length.max
```

После этого вычисляется:

```text
outcomeBits = log2(outcomes)
```

Для больших `big.Int` используется старшая значимая часть числа, чтобы получить `float64` без переполнения.

## 5.2. Поправка на запреты

Не все кандидаты, входящие в комбинаторное пространство, проходят правила:

* повторы;
* последовательности;
* dictionary;
* context.

Поэтому rejection rate оценивается эмпирически.

Используется:

```text
10 000 samples
```

Для каждого sample:

1. строится кандидат;
2. выполняется `rules.Check`;
3. кандидат после проверки затирается;
4. увеличивается счётчик rejected, если найдено нарушение.

Получаем:

```text
r = rejected / samples
```

Финальная оценка:

```text
bits = log2(outcomes) + log2(1 - r)
```

или эквивалентно:

```text
bits = log2(outcomes * (1 - r))
```

Если `r = 0`, используется исходное число бит.

Если `r >= 1`, допустимое пространство по результатам sampling считается вырожденным.

## Допущения

Оценка является нижней оценкой внутри используемой модели генерации, но не оценкой времени реального взлома.

Основные допущения:

* источник случайности является криптографически равномерным;
* unbiased primitives действительно дают равномерный выбор;
* комбинаторная модель соответствует алгоритму генерации;
* rejection rate правил оценивается конечной выборкой и поэтому имеет статистическую погрешность;
* внешняя информация об атакующем и человеческий выбор пароля не моделируются;
* оценивается политика генерации, а не конкретная строка пароля.

Для `history.window > 0` требуется дополнительный запас:

```text
requiredBits = log2(history.window) + 10
```

Если оценка политики меньше этого значения, политика считается слишком узкой для заданного history window.

# 6. Устройство пула и порядок остановки

Пул используется для предварительной генерации ограниченного количества паролей.

Основные поля:

```text
context + cancel
events channel
slots channel
config + RWMutex
WaitGroup
sync.Once
stopDone
```

Размер `events` и `slots` равен `issue.pool_size`.

`slots` ограничивает количество элементов, которые могут находиться в буфере.

Генерация выполняется фоновой goroutine.

## Получение элемента

`Get`:

1. проверяет context вызывающего;
2. проверяет context пула;
3. получает событие из `events`;
4. проверяет версию конфигурации;
5. возвращает слот после извлечения;
6. отдаёт готовый пароль вызывающему.

Если элемент был создан для старой версии политики, пароль затирается и элемент не возвращается.

## Остановка

`Stop` выполняется идемпотентно через:

```go
sync.Once
```

Порядок остановки:

1. вызывается `cancel()`;
2. фоновая goroutine получает отмену context;
3. `WaitGroup.Wait()` дожидается полного завершения генератора;
4. после завершения генератора канал `events` закрывается;
5. оставшиеся buffered events считываются;
6. каждый невыданный пароль затирается через `secret.Zero`;
7. закрывается `stopDone`;
8. все параллельные вызовы `Stop` дожидаются завершения через `stopDone`.

Таким образом:

* после `Stop` новые пароли не генерируются;
* goroutine не остаётся работать в фоне;
* невыданные пароли не остаются в буфере.

## Смена политики

`Reload` выполняется под `configMu`.

При смене политики:

1. уже находящиеся в `events` пароли извлекаются;
2. их буферы затираются;
3. слоты возвращаются;
4. устанавливается новая конфигурация;
5. увеличивается номер версии.

Если генерация старой версии уже выполнялась во время reload, перед помещением результата в `events` сравнивается version.

Устаревший результат затирается и не попадает потребителю.

Это позволяет менять политику без выдачи паролей, сгенерированных по старой конфигурации.

# 7. Хранилище истории и порядок операций при выдаче

Persistent store реализован на bbolt.

Каталог создаётся с режимом:

```text
0700
```

а файл:

```text
history.db
```

с режимом:

```text
0600
```

Основные записи находятся в bucket:

```text
records
```

Ключ записи — восьмибайтовый big-endian sequence number.

Значение — сериализованный `Record`.

```go
type Record struct {
	Subject       string
	Salt          []byte
	Hash          []byte
	IssuedAt      time.Time
	ExpiresAt     time.Time
	PolicyName    string
	PolicyVersion string
}
```

Открытый пароль в store не сохраняется.

## Hash

Для каждой выдачи создаётся отдельная случайная соль:

```text
16 bytes
```

Hash:

```text
SHA-256(salt || password)
```

При проверке повторного использования кандидат хешируется отдельно с солью каждой исторической записи.

Сравнение выполняется через:

```go
crypto/subtle.ConstantTimeCompare
```

Hash истории используется только для определения повторного использования пароля и не рассматривается как password authentication database.

## Metadata

Store также сохраняет metadata политики истории, необходимую для операций обслуживания:

```text
HistoryWindow
HistoryTTL
```

Это позволяет операциям GC и другим lifecycle-командам использовать параметры истории независимо от текущего CLI-процесса.

## Порядок выдачи

`issue.Issue` выполняет следующий цикл:

1. проверить context;
2. сгенерировать candidate через `generate.GenerateAttempt`;
3. если candidate нарушает policy rules — перейти к следующей попытке;
4. получить пароль кандидата как `[]byte`;
5. сгенерировать 16-байтовую соль;
6. вычислить SHA-256 hash;
7. создать `history.Record`;
8. вызвать `Store.Accept`;
9. внутри одной bbolt write transaction проверить history window;
10. если совпадения нет — записать новую history record;
11. если совпадение есть — не записывать запись, затереть candidate и повторить попытку;
12. при успехе вернуть пароль и metadata вызывающему.

Ключевое решение — проверка reuse и добавление новой записи объединены в `Store.Accept`.

Обе операции выполняются внутри одной bbolt write transaction.

Это предотвращает race вида:

```text
goroutine A: reuse check -> false
goroutine B: reuse check -> false
goroutine A: save
goroutine B: save same password
```

Поскольку bbolt сериализует write transactions, для одного store проверка и запись образуют единое атомарное действие.

## History window

Для субъекта записи упорядочиваются по:

1. `IssuedAt`;
2. sequence key при одинаковом времени.

Проверяются последние:

```text
window
```

записей.

Окно имеет приоритет над TTL: garbage collection не должна удалять запись, если она всё ещё входит в защищённое окно.

Если допустимые policy candidates генерируются, но каждый отклоняется историей, после исчерпания `attempts` возвращается:

```text
history_exhausted
```

Если кандидаты не проходят саму policy, возвращается:

```text
policy_too_strict
```

Разделение этих двух ошибок позволяет отличить слишком строгую политику от исчерпания пространства из-за истории.

# 9. Принятые технические решения и возможные направления развития

## Принятые решения

### Стандартная библиотека для критичных механизмов

Для криптографической случайности используется:

```text
crypto/rand
```

для hash:

```text
crypto/sha256
```

для constant-time сравнения:

```text
crypto/subtle
```

Собственные криптографические алгоритмы не реализуются.

### Зависимость random source

Источник случайности передаётся через небольшой интерфейс `Source`.

Это позволяет production-коду использовать `crypto/rand.Reader`, а тестам — controlled source без появления детерминированного режима в production CLI.

### Строгая политика вместо автоматического исправления

Ошибочная или неразрешимая политика отклоняется.

Генератор не уменьшает длину, не изменяет минимумы классов и не выключает forbid rules для получения результата.

### Ограниченные попытки

Все циклы generation/issue ограничены `attempts`.

Это исключает бесконечную генерацию даже при политике с очень высокой rejection rate.

### Trie вместо линейного словаря

Словарь преобразуется в поисковую структуру один раз.

Это увеличивает стоимость загрузки и расход памяти, но значительно уменьшает стоимость каждой последующей проверки пароля.

### bbolt для history

bbolt выбран как локальное embedded key-value хранилище с транзакциями.

Он позволяет объединить проверку reuse и запись новой history record в одну write transaction и обеспечивает сохранение истории между запусками процесса.

### Отсутствие plaintext password в history

Store содержит только:

```text
salt
SHA-256 hash
metadata
```

Пароль после выдачи не сохраняется.

### Секреты как `[]byte`

Пароли не хранятся как `string` без необходимости.

Буферы, которыми владеет приложение, затираются через `secret.Zero`.

### Детерминированный вывод

Порядок элементов, отчётов и rotation plan нормализуется перед сериализацией.

Это позволяет использовать golden tests и получать побайтово одинаковый результат при одинаковом входе.

### Атомарная запись

Файлы результатов, для которых важна целостность, записываются через `internal/atomicfile`.

Ошибка во время записи не должна оставлять частично сформированный файл как успешно созданный результат.

## Возможные направления развития

### Более компактное представление trie

Текущий trie использует:

```go
map[rune]*trieNode
```

в каждом узле.

Это обеспечивает простой и быстрый lookup, но имеет заметный memory overhead.

Для ещё более крупных словарей можно рассмотреть:

* radix tree;
* compact trie;
* DAWG;
* массивное или packed-представление рёбер.

Это может уменьшить memory footprint ценой более сложной реализации.

### Streaming build словаря

Текущая реализация сначала читает слова, затем строит trie.

В дальнейшем возможна вставка нормализованных слов в trie непосредственно во время чтения файла, чтобы уменьшить объём временных данных при загрузке.

### Confidence interval для rejection rate

Текущая entropy-модель использует эмпирический rejection rate на фиксированной выборке из 10 000 кандидатов.

Возможное развитие — использовать односторонний confidence bound для acceptance probability.

Это позволило бы учитывать sampling uncertainty непосредственно в численной нижней границе энтропии.

### Оптимизация history lookup

Текущая реализация корректна для заданного локального сценария и удовлетворяет требованию `history.window = 5`.

При значительно большем количестве записей можно добавить отдельный индекс по subject и времени выдачи, чтобы не собирать записи субъекта из общего bucket при каждой операции.

### Расширение persistent store

По условиям проекта одновременно работает один процесс.

Если потребуется multi-process или distributed deployment, слой `history.Store` можно заменить реализацией с необходимой моделью блокировок или внешней транзакционной БД, не меняя правила генерации и проверки паролей.

### Дополнительная автоматизация платформенных проверок

Проект ориентирован на Windows и Linux.

Для дальнейшего развития можно выполнять одинаковый набор:

```text
go test ./...
go test -race ./...
go vet ./...
make bench
make demo
```

в CI matrix для обеих платформ.
